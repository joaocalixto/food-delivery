Conceito 1

Monitoramento × Observabilidade

Monitoramento

Responde perguntas que você já sabia fazer antes: “CPU > 80%?”, “health UP?”.

É o dashboard da Aula 9. Útil, mas só enxerga o que alguém previu.

Observabilidade

Conseguir responder perguntas novas sobre o sistema só olhando o que ele emite — sem debugger, sem docker exec.

“Os pedidos do restaurante 3 estão mais lentos que os outros?” Ninguém previu a pergunta; os dados permitem responder.

Regra de bolso: se para responder você precisa entrar no container, o sistema não é observável.

Conceito 3

O que amarra os três: tags unificadas + trace_id

Três ferramentas separadas não são observabilidade. Correlação é: de uma métrica com pico você cai nos traces lentos; de um trace você cai nos logs daquela requisição.

Métrica

pico de erros em order-service

➜

Trace

os POST /orders vermelhos daquele minuto

➜

Log

AmqpConnectException com o mesmo dd.trace_id

Sem isso não funciona:

Tags unificadas em tudo

env · service · version em cada métrica, log e trace. No compose: DD_ENV=aula, DD_SERVICE=order-service, DD_VERSION=v2.

trace_id injetado no log

DD_LOGS_INJECTION=true põe dd.trace_id / dd.span_id no MDC. Com log em JSON, o Datadog liga log ↔ trace sozinho.

Conceito 5

Vocabulário para a prática

RED — Rate, Errors, Duration

As três métricas que todo serviço HTTP precisa ter num dashboard. O APM do Datadog gera as três sozinho para cada serviço.

Monitor = alerta

Uma condição sobre métrica, log ou trace que notifica alguém. “Error rate do order-service > 5% por 5 min → e-mail.”

SLO

Objetivo sobre uma métrica: “99% dos POST /orders em < 500 ms no mês”. O que sobra é o error budget.

Cardinalidade

Tag restaurant_id (dezenas de valores) é ok. Tag order_id (infinito) em métrica é o erro clássico — vira custo e lentidão. Isso vai em log/trace.

Passo 2 · 10 min

Subir o Agent — sem mexer no compose da Aula 10

Usamos um override de compose (docker-compose.datadog.yml): soma ao docker-compose.yml, não substitui.

docker compose -f docker-compose.yml \
  -f observabilidade-datadog/docker-compose.datadog.yml \
  up -d datadog-agent

docker compose exec datadog-agent agent status | head -60

O que o override liga no Agent:

DD_APM_ENABLED + DD_APM_NON_LOCAL_TRAFFICrecebe traces dos outros containers DD_LOGS_ENABLED + CONTAINER_COLLECT_ALLlê os logs de todos os containers pelo docker.sock DD_DOGSTATSD_NON_LOCAL_TRAFFICrecebe métricas custom dos outros containers

Mini-exercício: docker compose stop redis → o container some da lista em ~1 min. Religar.

O que ler no agent status, com ela:

  • API Keys status → “API Key valid”
  • Logs Agent → ligado
  • APM Agent → Receiver: 0.0.0.0:8126
  • DogStatsD → :8125/udp
✓Checkpoint  Infrastructure → Containers lista restaurant-service, order-service, rabbitmq, redis… com CPU/memória ao vivo.

Passo 3 · 10 min

Logs centralizados — o fan-out numa tela só

  1. Subir a stack toda com o override (up -d --build).
  2. Gerar tráfego pelo Postman: Register → List restaurants → Create order → Pay → List deliveries.
  3. Logs → Explorer, filtro service:order-service. Depois service:(order-processor OR delivery-service OR notification-service).
  4. O mesmo pedido aparece nos três — é o fan-out da Aula 5/6, agora numa timeline só.
✓Checkpoint  O log order.created de um POST /orders aparece em 4 serviços na mesma timeline.

Melhoria imediata: logs em JSON

Log em texto quebra o stacktrace em 40 linhas e não tem campos. Uma linha no application.yml resolve:

logging:
  structured:
    format:
      console: logstash

Rebuild, novo tráfego, e agora level, logger_name e message viram facetas filtráveis. Filtre status:error. O MDC (dd.trace_id) entra no JSON de graça.

Passo 4 · atenção

Spring Boot 4 é novo demais — tenha o Plano B pronto

Plano A — dd-java-agent (auto-instrumentação)

A matriz oficial do tracer lista Spring Boot até 3.x.

Na prática HTTP (Tomcat/servlet), JDBC, Lettuce e AMQP costumam instrumentar normalmente — são camadas abaixo do Boot.

Teste antes da aula. Se algum span faltar, vá para o Plano B sem drama.

Plano B — OpenTelemetry nativo do Boot

starter spring-boot-starter-opentelemetry (nativo do Boot 4).

O app exporta para o Agent:
management.opentelemetry.tracing.export.otlp.endpoint=http://datadog-agent:4318/v1/traces

O override já abre 4317/4318 no Agent (DD_OTLP_CONFIG_RECEIVER_*).

Bônus didático: ensinar os dois caminhos — “instrumentação automática por agente” × “OpenTelemetry (padrão aberto)”.

Antes da aula

Armadilhas — leia antes de começar

DD_SITE errado

Agent diz “API Key invalid” ou os dados somem. Conferir na URL da conta.

API key no Git

Só no .env; .env no .gitignore. Se vazar, revogar na hora.

Custo

Trial é grátis, mas Datadog cobra por host/container e GB de log. docker compose down no fim; não cadastrar cartão.

-javaagent depois do -jar

Não funciona. Tem que vir antes, como opção da JVM.

Logs multi-linha

Sem JSON o stacktrace vira 40 logs. Ligar logging.structured.format.console.

Boot 4 recente

Testar o tracer nos serviços antes; Plano B (OTLP) pronto.

Docker Desktop no Mac

Agent precisa do docker.sock montado; 7.61+ pode pedir pid: host (o override já faz).

Cardinalidade

Excesso de tags faz a conta explodir. Métrica = poucas dimensões.
